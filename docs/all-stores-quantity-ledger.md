# 所有店铺综合经营总览

入口 `/all-stores`，使用现有登录保护。各店铺原有订单、产品详情和财务表保持各自独立。

## 用户确认的统计口径

- 北京时间；每日数量以实际所属 FBS 供货单创建日期为准，而非订单原始下单日期或固定的 13:30 截止时间。
- 同一天多张供货单合并；每个 WB 组装订单编号计 1 件。店铺 ID 与订单编号共同构成身份，跨店相同编号不能相互覆盖。
- 供货单中的重复订单不重复累计，同时提示核对。新订单阶段客户取消的无效单排除。
- 尚未加入供货单、仍有效的新订单单列“待处理”；不提前放入某天的已处理数量。
- 退货使用 `completedDt` 实际取回时间，不使用申请时间、订单下单时间或客户取消时间。无取回时间的活动退货单列，归档取消记录不算待取回。
- 周一至周日为自然周；自定义周期切断自然周时标记非完整周，绝不读取周期外的数量补齐一周。
- 不计算金额。发货数量与取回退货数量独立列示，不自动相减。

## 来源、匹配与完整性

供货单列表来自 `GET /api/v3/supplies`；按 `next` 跟完所有分页，不能因为不足请求条数就判定结束。供货单实际订单 ID 来自 `GET /api/marketplace/v3/supplies/{supplyId}/order-ids`。订单资料与状态复用既有 FBS 加载器，新增成功读取时间 `fetchedAt`。退货复用新版 `GET /api/analytics/v1/item-returns`，读取活动及归档分页，再按取回时间筛选；请求窗口从 2024-01-01 开始，以免漏掉较早申请、本期取回的退货。

所有时间计算显式使用时区。带 `Z` 或偏移的时间按原时区解析；WB 未带时区的退货时间按莫斯科 UTC+3 解释，页面明确标注此规则。供货单没有有效时区时间时标记异常，不推测日期。

产品内部 SKU 和规格均一致才自动跨店合并；其他编码保持分店列示，提供单独的汇总 SKU 对应设置。用户明确对应后才合并。此设置不改写产品详情。退货优先在同店通过订单号/RID 对应商品，其次通过唯一的 WB 货号对应；歧义保留待核对。

每家店独立显示订单、供货单、退货的成功读取时间。读取失败、历史资料不完整或供货单订单缺失时提示，不能把缺失视为 0。API 的历史可用范围由 WB 决定；缺少历史商品资料时不会宣称周期完整。无有效 API 的已启用店铺仍列出错误，不能从所有店铺总数中静默忽略。

## 自动归档与持久化

Cloudflare Cron：`10 6,8,14 * * *`（UTC），即北京时间 14:10、16:10、22:10。定时任务自动发现全部已启用店铺，归档近 8 天；不依赖浏览器保持打开。页面打开时每 5 分钟再次读取，可手动刷新。店铺 API 沿用现有服务端加密管理，不返回浏览器。

沿用既有 Supabase/D1 `wb_sync_snapshots`：

- `all-stores-source:v2:<storeId>`：按店保存原始订单、供货单、退货及成功时间。
- `all-stores-supply:v1:<storeId>:<supplyId>`：单张供货单成功读取的订单 ID，长周期重试可复用。
- `all-stores-settings:v1`：SKU 对应，带版本和保存锁，避免多个页面相互覆盖。
- `all-stores-statement:v2:<uuid>`：完整数量快照，保存时由服务器重算，核对来源时间、覆盖、SKU 对应和设置版本。唯一 ID 保证后续同步不覆盖旧快照。

最近 30 份快照的索引保存于原 AUTH_KV 的 `all-stores-statement-summary:v1:` 前缀。快照正文存于上述数据库；索引不是正文。CSV 包含每日、每周、退货和逐笔来源，使用 BOM，并防止单元格公式注入。不完整导出会标记状态。

## 验证

自动测试覆盖真实批次跨天、跨店相同订单号、同天多供货单、无效取消、未分配新订单、重复编号、SKU 规格冲突、退货取回跨时区、自然周边界、分页缺失、日期校验、权限保护和页面服务端渲染。

现场通过 WB 官方接口核对真实供货单的订单 ID 集合，与计算后的总数量一致，缺失 ID 为 0。三个店铺均完成实时读取，并在浏览器验证上周汇总、退货明细、用户保存的 SKU 对应关系，以及数量快照保存后重新读回。本文不包含实际经营数量或供货单编号。
